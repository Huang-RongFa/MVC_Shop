# 04｜CI/CD、部署回滾與版本管理規範

## 1. 本章目的

正式上線後，每次修改都可能影響使用者下單、付款與後台操作。部署流程要可追蹤、可驗證、可回滾。

---

## 2. 分支與版本

建議至少區分：

```text
main：正式穩定版本
develop：開發整合版本
feature/*：功能開發
hotfix/*：正式環境緊急修正
```

版本命名可使用：

```text
v1.0.0
v1.0.1
v1.1.0
```

---

## 3. CI 檢查

每次合併前建議自動執行：

```text
□ dotnet build
□ dotnet test
□ npm install / npm ci
□ npm run build
□ Lint
□ 套件弱點掃描
□ 單元測試
□ API 測試
```

---

## 4. CD 部署流程

建議流程：

```text
1. 合併到指定分支
2. 自動建置後端
3. 自動建置前端
4. 部署到 Staging
5. 執行 Smoke Test
6. 人工核准正式部署
7. 部署 Production
8. 上線後觀察 Log 與 Metric
```

---

## 5. 資料庫變更

資料庫變更要特別小心。

檢查：

```text
□ Schema 變更有 SQL Script 或 Migration
□ 變更可重複執行或有保護
□ 先備份再改正式資料庫
□ 大資料表變更先評估鎖表風險
□ 有回滾 SQL 或修復方案
```

---

## 6. 回滾策略

```text
□ 後端保留上一版可部署 artifact
□ 前端保留上一版 build 檔案
□ 資料庫變更有還原方案
□ Feature Flag 可關閉新功能
□ 上線失敗時有明確負責人與流程
```

---

## 7. 本章總結

CI/CD 的目的不是追求自動化而已，而是降低上線風險。正式電商系統一定要能知道「這次上線改了什麼、誰核准、如何驗證、失敗怎麼退回」。
