# 05｜監控、日誌、告警與稽核規範

## 1. 本章目的

正式網站一定會遇到錯誤、流量尖峰或第三方服務異常。監控與日誌的目的，是讓開發者能快速知道發生什麼事、影響誰、如何修復。

---

## 2. Log 規劃

建議紀錄：

```text
□ Request Id / Trace Id
□ UserId
□ API Path
□ HTTP Method
□ Status Code
□ 執行時間
□ 錯誤訊息
□ 例外類型
```

避免紀錄：

```text
□ 明文密碼
□ 完整 Token 或完整 Cookie 值
□ 信用卡完整卡號
□ CVV / CVC
□ 個資完整內容
```

---

## 3. Metric 規劃

需要觀察：

```text
□ CPU
□ Memory
□ Disk
□ API 平均回應時間
□ API 錯誤率
□ DB 連線數
□ DB 查詢時間
□ 訂單建立數
□ 付款成功率
□ 金流 Callback 失敗數
```

---

## 4. Trace 規劃

重要流程需要串起來看：

```text
登入
  ↓
加入購物車
  ↓
建立訂單
  ↓
建立付款
  ↓
金流 Callback
  ↓
更新訂單狀態
```

Trace Id 可以幫助你從前端錯誤一路查到後端 API、Service、Repository 與資料庫操作。

---

## 5. 告警規劃

建議建立告警：

```text
□ API 5xx 錯誤率過高
□ 登入失敗次數異常
□ 付款 Callback 失敗
□ 訂單建立失敗
□ 資料庫連線失敗
□ CPU / Memory 過高
□ 磁碟空間不足
□ 備份失敗
```

---

## 6. 稽核紀錄

對應 MSSQL：

```text
AuditLogs
AdminActionLogs
SystemErrorLogs
UserLoginLogs
```

建議稽核：

```text
□ 管理員登入
□ 商品新增、修改、上下架
□ 庫存調整
□ 訂單狀態修改
□ 退款建立與核准
□ 優惠券新增與修改
□ 權限變更
```

---

## 7. 本章總結

Log 是查問題，Metric 是看健康狀態，Trace 是追流程，Alert 是主動通知。正式上線前，至少要能查詢錯誤、觀察 API 狀態，並在付款與訂單異常時收到告警。
