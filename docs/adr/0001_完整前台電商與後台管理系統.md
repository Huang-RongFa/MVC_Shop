# ADR-0001｜完整前台電商與後台管理系統

- 狀態：已採納
- 日期：2026-06-02
- 關聯文件：`00_總覽與正式上線架構.md`、`05_前台與後台Vue正式部署流程.md`、`06_RESTfulAPI前後台API與交易流程.md`

## 1. 背景與問題

本專案不是單純後台 CRUD，也不是教學用單表範例，而是一套要正式部署的交易型電商系統。資料庫與流程已涵蓋前台顧客購物、會員登入、購物車、訂單、付款、出貨、退款、優惠、庫存、權限與稽核紀錄。

若文件只描述後台管理或單表 CRUD，後續會導致 API、資料庫、前端與資安設計不足，特別是在訂單、付款、庫存與售後流程上容易出現資料不一致與權限漏洞。

## 2. 決策

本專案正式定位為：

```text
完整前台電商系統 + 後台管理系統 + ASP.NET Core Web API + 共用 MSSQL
```

系統必須同時支援：

```text
Storefront App：顧客瀏覽、註冊登入、購物車、結帳、付款、查詢訂單
Admin App：商品、庫存、訂單、付款、出貨、退款、優惠、使用者、權限、稽核管理
```

## 3. 理由

- 電商不是只有商品 CRUD，核心價值在交易流程與營運管理。
- 前台與後台的使用者、權限、DTO、API 語意不同，不能混成同一個管理系統。
- 正式部署時需同時考量顧客體驗、後台作業、資料一致性、資安、備份與監控。

## 4. 實作要求

```text
□ 文件不得把專案簡化為後台 CRUD
□ API 文件必須同時規劃 Storefront 與 Admin
□ 資料庫文件必須支援完整交易流程
□ 後端 Service 必須承載訂單、付款、庫存、退款等商業流程
□ 前端必須拆分顧客購物流程與後台管理流程
□ 正式部署前必須完成登入、權限、CSRF、CORS、Rate Limiting、監控與備份規劃
```

## 5. 影響與取捨

| 面向 | 影響 |
|---|---|
| 優點 | 架構能支援正式電商營運，不會停留在教學 CRUD |
| 成本 | 初期文件、API、Service 與測試規劃較多 |
| 風險 | 若只實作部分流程就上線，容易產生交易資料不一致 |

## 6. 驗收檢查

```text
□ 是否有前台顧客購物流程
□ 是否有後台管理流程
□ 是否有訂單、付款、出貨、退款、庫存與優惠流程
□ 是否有權限與稽核紀錄
□ 是否有正式部署資安與監控檢查
```
