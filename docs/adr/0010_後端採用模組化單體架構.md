# ADR-0010｜後端採用模組化單體架構

- 狀態：已採納
- 日期：2026-06-02
- 關聯文件：`00_總覽與正式上線架構.md`、`02_後端分層Repository與Service.md`、`03_Program與Middleware安全管線.md`

## 1. 背景與問題

本專案需要支援完整電商交易流程，但目前仍處於一邊學習、一邊正式部署的階段。若初期直接拆成微服務，會增加服務部署、服務間通訊、分散式交易、監控、除錯與維運成本。

## 2. 決策

後端初期採用單一 ASP.NET Core Web API 應用程式，內部依業務模組分層與分組。

```text
MySystem.Api
MySystem.Application
MySystem.Domain
MySystem.Infrastructure
```

內部模組包含：

```text
Accounts
Catalog
Inventory
Orders
Payments
Shipments
Refunds
Promotions
Auditing
```

## 3. 理由

- 單一部署單元較容易學習、除錯與正式部署。
- 跨表交易可直接透過資料庫 Transaction 控制。
- 模組邊界仍可透過資料夾、命名空間、Service、Repository 與 DTO 維持。
- 未來若流量、團隊與部署需求成熟，再評估拆分微服務。

## 4. 實作要求

```text
□ Controller 不直接操作 DbContext
□ Service 負責商業流程與交易規則
□ Repository 負責資料查詢與儲存
□ Entity 不直接回傳前端
□ 前後台 Controller 分界
□ 重要流程使用 Transaction
□ 模組之間避免任意互相存取資料
□ Program.cs 註冊邏輯拆成 Extension Method
```

## 5. 影響與取捨

| 面向 | 影響 |
|---|---|
| 優點 | 部署簡單、交易一致性較容易控制 |
| 成本 | 單一應用程式需維持良好模組邊界 |
| 風險 | 若不遵守分層，會退化成大型混亂單體 |

## 6. 驗收檢查

```text
□ 是否存在清楚 Application / Domain / Infrastructure 分層
□ Controller 是否只呼叫 Service
□ 訂單、付款、庫存、退款是否集中在 Service 控制
□ DbContext 是否未散落在 Controller
□ API 是否可獨立部署成單一 Web API
```
