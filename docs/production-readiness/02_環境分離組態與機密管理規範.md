# 02｜環境分離、組態與機密管理規範

> 版本：2026-06-02  
> 文件目的：避免測試資料、測試金流、開發金鑰或正式機密混用，降低資料外洩與部署事故風險。

---

## 1. 本章目的

正式電商系統不應只有一個環境。開發、測試、正式環境要分開，避免測試資料、測試金流或開發機密誤用到正式環境。

---

## 2. 建議環境

| 環境 | 用途 | 注意事項 |
|---|---|---|
| Development | 本機開發 | 可使用測試資料，不連正式金流，不接正式資料庫 |
| Staging | 上線前驗收 | 盡量接近正式環境，但資料與金鑰仍不可混用 Production |
| Production | 正式營運 | 嚴格控管權限、資料、機密與操作流程 |

---

## 3. 組態管理

不同環境應使用不同設定：

```text
appsettings.Development.json
appsettings.Staging.json
appsettings.Production.json
```

但正式機密不要直接寫進檔案。正式環境應由下列方式提供：

```text
□ Environment Variables
□ User Secrets（僅本機開發）
□ Key Vault / Secret Manager
□ CI/CD Secret Variables
□ Docker / Kubernetes Secret
□ 雲端平台受控機密服務
```

---

## 4. 機密資料清單

```text
□ MSSQL 連線字串
□ Cookie / Token 簽章金鑰
□ Data Protection Key 儲存位置與保護金鑰
□ 金流 API Key / Merchant Secret
□ 物流 API Key
□ SMTP 密碼
□ 雲端儲存金鑰
□ 第三方登入 Client Secret
□ 後台管理員初始密碼或邀請碼
```

以上資料不應進入 Git、前端程式碼、公開文件、Issue 截圖或 Log。

---

## 5. .gitignore 與外洩預防

建議加入：

```gitignore
.env
.env.*
appsettings.Production.json
*.pfx
*.key
*.pem
secrets.json
service-account*.json
```

CI/CD 應加入：

```text
□ Secret 掃描
□ NuGet 套件弱點掃描
□ npm 套件弱點掃描
□ Docker Image 掃描（若使用容器）
□ 禁止把 Production Secret 寫入 Artifact
```

---

## 6. 機密輪替

正式環境要規劃 Key Rotation。

```text
□ Cookie / Token 簽章金鑰可輪替
□ Data Protection Key 可持久化並安全保存
□ 金流金鑰可更換
□ 物流金鑰可更換
□ 資料庫帳號密碼可更換
□ 離職人員權限可撤銷
□ API Key 外洩時有應變流程
```

輪替時要注意：若 Cookie / Data Protection Key 立即失效，使用者可能全部被登出；正式輪替前應評估影響。

---

## 7. 權限最小化

```text
□ 應用程式資料庫帳號只給必要權限
□ 開發人員不直接操作正式資料庫
□ 正式伺服器登入需留紀錄
□ 後台管理員角色分級
□ 金流退款權限需額外限制
□ 下載個資、匯出報表需額外權限與稽核紀錄
□ CI/CD 帳號只給部署所需權限
```

---

## 8. 正式資料使用規範

```text
□ Production 資料不可直接複製到本機開發
□ 若要用正式資料除錯，應先匿名化或遮罩
□ 匯出資料需記錄操作者、時間、原因
□ 測試帳號不可擁有正式高權限
□ Demo 或截圖不可包含真實個資、訂單、付款資料
```

---

## 9. 本章總結

環境分離是避免事故的第一道防線。正式上線前，要確認 Development、Staging、Production 的資料庫、金流、物流、Cookie / Token 簽章金鑰、CORS 網域、Log 與權限都彼此分離。
