# 05｜監控、日誌、告警與稽核規範

> 版本：2026-06-02  
> 文件目的：讓正式網站發生錯誤、流量尖峰、金流異常或資料問題時，可以快速定位、通知與修復。

---

## 1. 本章目的

正式網站一定會遇到錯誤、流量尖峰或第三方服務異常。監控與日誌的目的，是讓開發者能快速知道發生什麼事、影響誰、如何修復。

---

## 2. Log 規劃

建議紀錄：

```text
□ TraceId / RequestId
□ UserId 或匿名 Session Id
□ API Path
□ HTTP Method
□ Status Code
□ 執行時間
□ Client IP（注意個資與代理轉發）
□ User Agent
□ 錯誤訊息
□ 例外類型
□ 重要業務事件 ID，例如 OrderId / PaymentId / ShipmentId
```

避免紀錄：

```text
□ 明文密碼
□ 完整 Token 或完整 Cookie 值
□ 信用卡完整卡號
□ CVV / CVC
□ 個資完整內容
□ 金流或物流 API Key
□ Connection String
```

---

## 3. Metric 規劃

需要觀察：

```text
□ CPU
□ Memory
□ Disk
□ API 平均回應時間
□ API P95 / P99 回應時間
□ API 4xx / 5xx 錯誤率
□ DB 連線數
□ DB 查詢時間
□ 訂單建立數
□ 付款成功率
□ 金流 Callback 失敗數
□ 登入失敗次數
□ Rate Limit 觸發次數
□ Queue 長度（若未來加入背景任務）
```

---

## 4. Trace 規劃

重要流程需要串起來看：

```text
登入
  ↓
加入購物車
  ↓
建立訂單
  ↓
建立付款
  ↓
金流 Callback
  ↓
更新訂單狀態
```

TraceId 可以幫助你從前端錯誤一路查到後端 API、Service、Repository 與資料庫操作。

---

## 5. Health Check 規劃

建議拆成：

```text
/health/live   檢查應用程式是否活著
/health/ready  檢查是否可接受流量，例如 DB、必要第三方服務是否可用
```

檢查項目：

```text
□ API Process 正常
□ MSSQL 可連線
□ 重要外部服務可用性
□ 磁碟空間
□ 記憶體狀態
```

Ready Check 不應暴露詳細內部資訊給公開網路，必要時只允許 Load Balancer、監控服務或內部網路存取。

---

## 6. 告警規劃

建議建立告警：

```text
□ API 5xx 錯誤率過高
□ API P95 回應時間過高
□ 登入失敗次數異常
□ 付款 Callback 失敗
□ 訂單建立失敗
□ 資料庫連線失敗
□ CPU / Memory 過高
□ 磁碟空間不足
□ 備份失敗
□ 金流或物流第三方服務異常
□ 大量 401 / 403 / 429
```

告警要包含：

```text
□ 發生時間
□ 影響系統
□ 主要錯誤訊息
□ TraceId 或查詢線索
□ 處理負責人
□ 升級通知方式
```

---

## 7. 稽核紀錄

對應 MSSQL：

```text
AuditLogs
AdminActionLogs
SystemErrorLogs
UserLoginLogs
```

建議稽核：

```text
□ 管理員登入
□ 商品新增、修改、上下架
□ 庫存調整
□ 訂單狀態修改
□ 退款建立與核准
□ 優惠券新增與修改
□ 權限變更
□ 匯出報表或個資
□ 金流與物流關鍵狀態異動
```

稽核資料不應允許一般後台人員刪除。若需要保存期限，應規劃歸檔或唯讀保留策略。

---

## 8. 本章總結

Log 是查問題，Metric 是看健康狀態，Trace 是追流程，Alert 是主動通知。正式上線前，至少要能查詢錯誤、觀察 API 狀態，並在付款、訂單、登入與資料庫異常時收到告警。
